# Warp mobile agent client
## Current feature status
The password-gated mobile chooser lists local Warp **agent runs**, with optional cloud/all filters, descriptions, age, status, and reported credit/approximate USD cost. A selected run shows a scrollable conversation with User, Agent, and Tool cards; tool calls show command/input without expansion and results remain under an Output disclosure. Calls/results are paired only when supplied action IDs match. X returns to the chooser without stopping a run. History loads the latest ~8 KiB by default (4–16 KiB configurable), prepends older turn windows on upward scroll, and polls active runs every six seconds. Metadata polling updates status and automatically enables continuation once an external CLI run finishes. Authenticated direct links use `?run=<runId>`.
New session starts a local CLI process on this machine. The composer continues finished `CLI / LOCAL` conversations by launching another local CLI run with the same conversation ID, including runs created outside warpweb. Both textareas support Ctrl+Enter submission; Enter remains a newline. User cards appear before POST completion, retain rejected input for edit/retry, and remain visible through progress/run transitions. Submission and render callbacks are guarded against unrelated-view updates. Pending cards, their original task text, and the bounded render cache live only in page memory; canonical Warp history may contain the private-task-file instruction rather than the literal submitted task after a page reload.
Jobs are polled every 2.5 seconds. The CLI-reported run ID is exposed during execution only after REST verifies `CLI / LOCAL`, allowing canonical tool history to load before process completion. CLI text progress remains a bounded fallback; unavailable command/output is not fabricated. There is no WebSocket transport. Desktop/active runs remain read-only inside warpweb; a validated upstream Warp shared-session link is offered when present, with edit access required for steering there.
## Browser options
`app/static/preferences.js` stores validated options, recent directories, and up to 100 conversation prompt counters in `localStorage` under `warpweb.preferences.v1`. No prompts, passwords, or API keys are saved there. Settings are per browser/device, with in-memory fallback if storage is disabled:
- MRU directory limit: default 20, range 1–100. Both cwd inputs share suggestions and remain editable. Record the canonical cwd from accepted submissions, deduplicate, trim immediately on limit changes, and provide clear-history control. Clearing suggestions does not change the selected cwd or server workspace restrictions.
- History request window: default 8 KiB, range 4–16 KiB; applies to initial, older, and newer requests.
- Conversation-card initial preview: default 12 lines, range 4–40, with Show more/Show less controls. Chooser descriptions retain their two-line default.
- Cost-refresh cadence: every N accepted prompts, default 1, range 1–100. Opening a run always fetches current usage. At cadence thresholds, refresh once the new run is verified and again at completion, with up to four running-job usage attempts. Status polling is independent. Missing/late usage is marked pending, refresh failures retain the last known value, and a value carried from a previous run is explicitly labeled Last refreshed run cost. Figures are reported run usage, not an accumulated conversation total or account balance.
The Options gear is available in authenticated chooser/new/session views; Reset options restores defaults without deleting MRU history or counters.
## Data schema and API
There is **no database**. Expiring browser sessions, login attempts, and up to 100 active/recent jobs are in memory; restarting the service loses those records, not Warp runs. A job stores an opaque random ID, state, run ID, verification flag, conversation ID, canonical cwd, original prompt (at most 4096 characters), generic error, and at most 16 KiB of progress output. Public jobs contain `id`, `state`, `run_id` (null until verified), `conversation_id` (null until verified), `cwd`, `prompt`, `output`, and `error`. A per-job mode-0600 task file in `~/.local/state/warpweb/jobs/<id>/task.txt` holds the prompt while the CLI runs and is removed afterward. Warp persists conversations and usage.
The server uses only `GET /agent/runs` (cursor, sort, execution location), `GET /agent/runs/{runId}`, and `GET /agent/runs/{runId}/conversation` through server-only `WARP_API_KEY`. Browser endpoints:
- `GET /api/session`, `POST /api/login`, `POST /api/logout`: password-gated browser session management.
- `GET /api/runs?scope=local|cloud|all&cursor=...&limit=...`: bounded chooser cards with usage and capabilities.
- `GET /api/runs/{runId}`: detail/capabilities plus conversation-availability probe. `GET /api/runs/{runId}/metadata`: the same card metadata without fetching history, for inexpensive status/usage refresh. Cards include `can_send`, local-CLI `conversation_id`, and a validated `session_link`.
- `GET /api/runs/{runId}/history?size=8192&before=<turn-index>|after=<turn-index>`: bounded actor turns; returns start/end cursors and older/newer flags. Each turn contains actor, title, timestamp, body, tool/continued flags, block ID, zero-based fragment index, total fragment count, content kind (`text`, `action`, `action_result`), and optional supplied action ID. Block identity uses upstream message ID when available, otherwise traversal index; adjacent fragments of a block are rejoined in the browser. Invalid cursors return 409 and trigger a recent-history reload.
- `POST /api/render`: accepts `{text}` under authentication and Origin validation; returns sanitized `{html}` or null for plain-text fallback. Source is capped at 64 KiB UTF-8 (and 65536 characters at request validation), HTML at 256 KiB. Incomplete blocks and larger text stay plain; the browser caches up to 32 render results.
- `POST /api/jobs`: prompt and optional cwd to start a local task. `GET /api/jobs/{jobId}`: job status, verified live run ID, canonical cwd, original prompt, and bounded progress. `POST /api/runs/{runId}/messages`: finished local CLI continuation only.
`python3 -m tools.hash_password` prompts without argv and prints a random-salt PBKDF2-HMAC-SHA3-256 `WARP_API_HASH=...` verifier for private storage. Its `--env-file` option instead atomically updates a mode-0600 environment file without printing the verifier; other entries are preserved.
## Installation tooling
`INSTALL.md`, linked from the README, documents the Personal-token flow and local/public setup. `INSTALL.sh` runs the standard-library `tools/install.py` helper. `--check`/`--help` are non-destructive; interactive setup creates/reuses `.venv`, installs server requirements, collects a hidden token, invokes the non-printing password hasher, and writes mode-0600 credentials under `~/.config/warpweb/warpweb.env` plus a user systemd unit with absolute checkout-specific paths. No secrets are passed in argv or written into the unit. The config directory and private backups are mode 0700, with at most 25 backups per replaced file. Replacing an existing installation requires REPLACE confirmation; enabling/start/restart requires a separate confirmation. `--no-start` installs configuration/unit and daemon-reloads but does not restart.
Installer defaults are loopback-only HTTP at `127.0.0.1:8797`, exact allowed Origin, Secure cookies/HTTPS enforcement disabled for this local mode, and cwd roots restricted to the checkout. Explicit HTTPS origins enable Secure cookies and HTTPS enforcement; `WARPWEB_PUBLIC_URL` supplies the validated redirect origin. No personal hostname is embedded in the source; public deployments must explicitly configure `WARPWEB_ALLOWED_ORIGINS` and `WARPWEB_PUBLIC_URL` privately. Missing or invalid public-origin configuration returns 503 rather than redirecting to untrusted input. Existing public deployments must set the public URL before their next restart. TLS/DNS/proxy installation and lingering remain operator responsibilities. Generated units log to the user journal; the existing personal service's file logging remains unchanged until explicitly replaced.
`.gitignore` excludes credentials/environment files, runtime data/logs, backups, Python/native build output, caches, virtual environments, editor metadata, the current local screenshot captures, and the three personal installed deployment snapshots. Portable examples under `deploy/*.example` are tracked instead; personal files are not deleted or applied to the current service.
Generated units use unquoted path directives with escaped systemd specifiers; `/usr/bin/env` launches the quoted virtualenv executable so checkout paths containing spaces, dollar signs, percent signs, or quotes remain usable. Unsafe raw path endings/control characters are rejected before installation changes. Regression coverage runs the real systemd unit parser without installing or starting a unit.
## Business and security rules
The service fails closed without the password verifier or Warp API key, does not expose the key to the browser, and sets Secure/HttpOnly/SameSite cookies, no-store, HSTS, and a restrictive CSP. Browser sessions last twelve hours; five failed logins per IP block further attempts for fifteen minutes. Every mutating request requires the public HTTPS Origin. Passwords and user prompts are never placed in CLI arguments.
The CLI gets a fixed instruction to read the private task file, uses `--no-snapshot`, and may only work inside configured local roots (`/home/michael`, archive projects, `/tmp/warpweb`). A maximum of two jobs run at once, with a fifteen-minute process timeout. Same-conversation local jobs are rejected while one is already running. Preview and submission share capability checks: only `CLI / LOCAL` with a valid conversation UUID and state `SUCCEEDED`, `FAILED`, `ERROR`, or `CANCELLED` can continue; unknown, queued, claimed, pending, running, and blocked states are not writable.
Live and completed run IDs are exposed only after REST confirms `source=CLI` and `execution_location=LOCAL`; live verification makes at most four attempts, with completion verification retaining its four-attempt retry. Cloud creation is never used. The installed CLI and researched public REST API/SDK expose no active-run messaging endpoint; desktop control is not emulated. Shared-session links must be HTTPS on `app.warp.dev` or `oz.warp.dev`, with no embedded credentials or nonstandard port. No session is automatically shared.
The public API supplies whole normalized conversations, not a server-side stream/history cursor; this backend paginates turns, splitting long bodies into small Unicode-safe parts. Tool inputs/results remain readable plain text. Prose uses `markdown-it-py` CommonMark/table rendering with raw HTML disabled and `nh3` tag/attribute sanitization; scriptable URL schemes, remote images, comments, and active markup are excluded. HTML is inserted only from the authenticated sanitizer endpoint, and CSP is unchanged. Partial-block rendering intentionally falls back to plain text until all adjacent fragments have loaded.
## Deployment and known constraints
The enabled user systemd service is loopback-only on `127.0.0.1:8797`; stdout/stderr are private under `/tmp/warpweb`. Its CLI path is explicitly `/home/michael/.local/bin/warp`. The 30-day personal key is loaded from `/home/michael/.config/warpweb/warpweb.env`; the password hash was imported into the user systemd manager from the user's shell, so a manager restart/reboot may require reimport or a private persistent file. The service restart clears browser login/job state and terminates local jobs; the persisted Warp runs remain accessible.
The private deployment uses Cloudflare Tunnel, whose `/etc/cloudflared/config.yml` routes its privately configured hostname directly to `http://127.0.0.1:8797`; the other ingress rules were retained. Browser HTTPS terminates at Cloudflare's trusted edge certificate, travels over the encrypted tunnel, and uses HTTP only on loopback. The Warp Nginx template is not used and no local public certificate is required. `deploy/cloudflared-config.yml` is the ignored installed ingress snapshot; dated pre-change copies are under `backup/deploy/`.
The October 12 UX implementation was activated by an approved `warpweb.service` restart on October 12, 2026, at approximately 13:32 UTC. Before restarting, the service cgroup contained only uvicorn and the job directory contained no private task files; no active warpweb CLI jobs were detected. Afterward the service remained active/running with zero automatic restarts. Browser sessions were cleared. Compatibility remains: the frontend falls back to the existing run-preview endpoint if `/metadata` is unavailable and shows plain text if `/render` is unavailable. Future restarts require approval/checking active jobs because they clear authentication/job records and terminate running local agents.
The service explicitly enables Secure cookies, public-only allowed Origin, and HTTPS enforcement using trusted loopback proxy headers.
